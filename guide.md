# Editorial guide

Read the whole article and identify the reader's task before adding visuals.
A visual earns its place by explaining the adjacent text, not by meeting an
image quota. Preserve titles, slugs, cover images, structure, links, language
and publication state unless the assigned change requires a specific correction.
Keep existing drafts unpublished.

## Choose the visual that answers the reader's question

| Reader needs to understand | Use | Content requirements |
| --- | --- | --- |
| Where to click or how the actual interface represents a rule | `screenshot` | Capture the real application, use demonstration data, retain enough surrounding context and include descriptive alt text. |
| What a customer would read or how they might respond | `messages` with one panel | Write a complete, plausible example and identify its channel, business and relevant context. |
| Why context changes the message | `messages` with two panels | Compare the same situation or clearly name the two audiences. Tabs show one phone at a time; keep each message focused and complete. |
| A one-off screenshot specific to an article | The publishing project's existing figure/attachment integration | Keep the original asset, accessible description and full-size link. |

Use images for evidence of the interface and HTML components for message
content. Do not recreate an application screen as an invented screenshot or
rasterize message text. Names, conversations, benefits and outcomes in the
message catalog are illustrative; their accessible captions say so. Examples demonstrate
concrete use cases and are not customer testimonials, sent campaigns or proof
of performance.

Place a visual after the paragraph that establishes its purpose. One visual
should explain one idea. The surrounding prose establishes what to notice.
Caption data describes the figure for assistive technology, including whether
it shows a real interface with demonstration data or an illustrative message;
it is not displayed below the figure.
Screenshots should avoid unrelated navigation, private customer data and
unreadably small full-screen captures. Keep original proportions; the reader
can open the source image at full size.

## Help Center articles

Explain a real task in the current interface. Place each screenshot immediately
after the instruction or state it illustrates. Name the exact control in the
text, such as **Nuevo Segmento**, so the step works without seeing a pointer.
Do not capture every trivial click. Prioritize unfamiliar controls, choices,
configuration logic and the resulting state. Avoid repeating nearly identical
screens just to increase the number of images.

Use neutral Spanish with tú. Match screenshots to the article language and the
actual interface labels. Adapt published translations; do not replace localized
screens with a different-language interface without recording the limitation.

Use the existing visual components. Do not add visible headings above phones or
visible descriptive captions below their stages. Provide accessible names,
image alternative text and illustrative-case context in the supported metadata;
explanatory prose remains in the article. Comparison tabs label the alternatives.

See [screenshot standards](screenshots.md), [message examples](messages.md) and
[the publishing workflow](workflow.md). Rendering dimensions, channel shells,
validated payload fields and export commands belong to the application's local
integration guide, not a second renderer in this repository.
