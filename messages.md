# Message examples

Use the application's implemented channel components and validated authoring
contract. The editorial schema describes examples, not the sending APIs. Do not
invent channel capabilities or reproduce message text as a screenshot.


**Established — 2026-09-20.** Every offered conversation example includes a
useful action in the first business send. A customer's initial question may
precede it in support examples, but the first answer delivers the relevant link,
button or product action without asking whether the customer wants it. Later
replies can clarify preferences or delivery; they do not unlock the offer.

Use a product image plus an action for a specific item, and a short carousel
with an action on each card for distinct alternatives or complementary products.
When a message includes a carousel, keep its accompanying text free of buttons:
the product cards provide the actions. Send the introduction and cards together
before any customer reply, without adding a duplicate introductory CTA.
A second view of the same item is another product image, not another recommendation.
Do not add unrelated products to service examples: tracking, pickup details and
benefits need their own useful action. A generic comparison also includes a CTA,
so the comparison demonstrates relevance rather than a missing button.

SMS uses an illustrative URL in the message text instead of imitating a WhatsApp
button. **Established — 2026-09-21:** Spanish SMS examples end with the exact
opt-out wording `BAJA para salir`, without an unsubscribe URL. Preserve the
useful commercial link (for example, a product, cart or recommendation); this
rule changes only the opt-out text. Apply it to new examples and revisions of
published examples in articles, guides, the library and Help exports.
Email and Push are complete single-message compositions; their image,
copy and action can remain separate ordered blocks within that one message.
All example actions stay inert. Demo links use reserved `example.com` addresses.
This is an editorial authoring rule, not a restriction on customer-authored
content or a claim about outbound API capabilities.

## Reuse and verification

Keep the editable source definition with the consuming article. Identify cases
as illustrative in accessible metadata; never fabricate testimonials, customer
results or performance evidence. Product images must be relevant and available.
Use the actual image asset, not a placeholder URL presented as a loaded product.

Preview every panel and verify image loading, card scrolling, tab selection by
mouse and keyboard, and action labels. Example actions are inert: testing them
must not contact a customer, submit a campaign or open a purchasing workflow.
For configuration articles, add a message example only when it explains the
result of that configuration. A screenshot may be all the article needs.
